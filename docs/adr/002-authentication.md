# ADR-002: Аутентификация и роли

**Статус:** принято.

## Решение
- **Вход**: OAuth2 password flow (`POST /auth/login`), с ним работает Authorize в Swagger. Открытой регистрации нет, первый admin создаётся через CLI (`make user`).
- **Токен**: HS256 JWT с минимумом полей: `sub` (id пользователя), `iat`, `exp`. Роль в токен не кладётся и читается из БД на каждый запрос.
- **Роли**: `officer < captain < admin`, старшая роль включает права младших («officer+» в ТЗ). Проверка — доменный метод `User.ensure_role`, в HTTP он подключается зависимостью `require_role`.
- **Пароли**: argon2id (pwdlib), хеширование в `asyncio.to_thread`.

## Почему так
- **Роль из БД, а не из токена**: смена роли или удаление пользователя срабатывают сразу, а не по истечении токена. Плата — один SELECT по первичному ключу на запрос. При нагрузке — кеш или роль в токене с коротким TTL.
- **`algorithms=["HS256"]` явно**: закрывает подмену `alg`, включая `none`. Обязательны `exp` и `sub`.
- **Единый ответ 401** «Incorrect email or password»: по ответу нельзя понять, существует ли email.
- **Фиктивная проверка хеша**: если пользователя нет, хеш всё равно проверяется. Время ответа одинаковое, и по таймингу email не перебрать.
- **argon2 в потоке**: хеширование нагружает CPU примерно на 50 мс и иначе блокировало бы event loop для всех запросов.
- **`JWT_SECRET` обязателен и не короче 32 символов**: без него приложение не стартует, работа с известным секретом исключена.
- **Пароль в CLI** берётся только из `getpass` или переменной окружения: аргумент остался бы в истории shell и в выводе `ps`.

## Не сделано сейчас
Ограничение частоты попыток входа (rate limit) — день 15 по плану.
