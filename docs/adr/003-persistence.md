# ADR-003: Хранение — Repository и Unit of Work поверх SQLAlchemy

**Статус:** принято.

## Решение
- **Repository и Unit of Work — порты** модуля (`ports.py`). SQL-реализации лежат в `adapters/persistence.py`.
- **ORM-записи** (`UserRecord`) отделены от доменных сущностей (`User`, frozen dataclass). Репозиторий отдаёт только доменные объекты.
- **Одна транзакция на сценарий**: `async with uow: ... await uow.commit()`. Без `commit()` изменения откатываются.
- **Сервис получает фабрику UoW, а не экземпляр.** Сервис живёт всё время работы приложения, а у каждого вызова своя сессия, поэтому параллельные запросы не делят одну сессию.
- **Нарушения ограничений БД переводятся в доменные ошибки.** `IntegrityError` по уникальному email становится `EmailAlreadyRegisteredError`, проверки «SELECT перед INSERT» с гонкой между двумя регистрациями нет.

## Почему не «сервис сам работает с AsyncSession»
Тогда сервис зависел бы от SQLAlchemy: без БД его не протестировать, а транзакционные правила размазываются по коду. Unit of Work даёт одну явную точку фиксации, а сервис тестируется на in-memory фейках.

## Как проверяется
- **Контрактные тесты**: один набор (`tests/integration/identity/test_unit_of_work_contract.py`) гоняется и на фейке, и на Postgres. Если фейк разойдётся с реальностью, unit-тесты перестанут что-либо доказывать — этот набор такое расхождение ловит.
- **Схема в тестах** строится настоящими миграциями Alembic, каждый тест откатывает свою транзакцию.
