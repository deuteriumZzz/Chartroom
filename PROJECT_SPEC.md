# ТЗ: Chartroom

Демонстрационный backend-проект «ассистент по судовым процедурам и отчётам».
Автор ТЗ: роль «архитектор + старший разработчик». Статус: согласовано, в работе (дни 1–5 выполнены).

---

## 1. Цель и границы

**Цель.** Показать работодателям (backend + AI + морская тематика) связку: знание судового документооборота + умение построить надёжный RAG-сервис и агента с вызовом функций.

**Это демонстрация, не продукт.** Не позиционируется как production. Реальных данных судоходных компаний нет, корпус документов синтетический.

**Решаемые боли (подтверждены автором):**
1. Быстро найти нужную процедуру SMS/ISM (тревога, аудит, проверка PSC) и увидеть, где именно это написано.
2. Отчёты и чек-листы вручную: ошибки, пропущенные поля, дубли.

**Входит в объём (MVP):**
- M1. Вопросы по процедурам со ссылками на источник и отказом «в документах нет ответа».
- M2. Извлечение структурированных отчётов и чек-листов из свободного текста с проверкой полноты.
- M3. Оценка качества поиска и ответов на размеченном наборе вопросов.
- M4. Агент с вызовом функций: модель по ходу ответа сама запрашивает данные (процедуры, отчёты, шаблоны) через Gemini function calling.

**Не входит (backlog):** PMS и техобслуживание, анализ рейсов, обмен «судно — берег», мобильное приложение, мультитенантность, реальные интеграции с судовыми системами, инструменты агента с записью данных.

## 2. Пользователи и роли

| Роль | Права |
|---|---|
| `admin` | загрузка и версионирование документов, управление пользователями и шаблонами отчётов |
| `captain` | вопросы, отчёты, просмотр журнала запросов всех |
| `officer` | вопросы, отчёты, просмотр своего журнала |

Роли иерархичны: `officer < captain < admin`, старшая включает права младших (ADR-002).

## 3. Функциональные требования

### M1. RAG по процедурам
- FR-1. Загрузка PDF/DOCX/TXT/MD с метаданными (название, версия, язык, дата).
- FR-2. Асинхронная индексация (парсинг → чанки → эмбеддинги → Qdrant), статус задачи доступен по API.
- FR-3. Вопрос на русском или английском → ответ на языке вопроса.
- FR-4. Каждый ответ содержит цитаты: документ, раздел (путь заголовков), страница, фрагмент текста.
- FR-5. Если релевантных фрагментов недостаточно — отказ с текстом «В загруженных документах ответа нет» (без догадок).
- FR-6. Проверка цитат: каждая ссылка в ответе должна указывать на фрагмент, реально переданный в контекст модели; иначе ссылка удаляется, ответ помечается `citation_warning`.
- FR-7. Обратная связь на ответ (полезен/нет, комментарий).
- FR-8. Версионирование: новая версия документа не теряет старую; поиск по умолчанию только по актуальной.

### M2. Отчёты и чек-листы
- FR-9. Шаблоны отчётов задаются JSON-схемой (поля, типы, обязательность, диапазоны).
- FR-10. `POST /reports/extract`: текст отчёта + шаблон → заполненная структура (structured output).
- FR-11. Валидация: обязательные поля, типы, диапазоны, согласованность (например, ROB не отрицательный). Результат: `data` + `issues[]` (поле, причина).
- FR-12. Сохранение отчёта, статус `draft | needs_review | accepted`.
- FR-13. Стартовый набор шаблонов (подтверждён автором): суточный отчёт, чек-лист учебной тревоги, швартовая операция.

### M3. Оценка качества
- FR-14. Золотой набор `eval/golden.yaml`: 30 вопросов (20 с ответом, 5 без ответа, 5 на другом языке) с ожидаемым разделом.
- FR-15. Команда `make eval` считает: hit@k (нужный раздел в топ-k), MRR, точность отказов, корректность цитат, долю ответов с `citation_warning`. Результаты сохраняются в `eval/results/*.json` и подставляются в README.

### M4. Агент с вызовом функций
- FR-16. `POST /agent/ask`: вопрос на естественном языке. Модель получает объявления функций (`tools` → `function_declarations` в Gemini API), возвращает структурированный вызов (имя + аргументы), сервис выполняет его и возвращает результат модели (`function_response`), затем модель формирует ответ.
- FR-17. Инструменты, только на чтение (список подтвердить автором): `search_procedures(query, top_k)`, `list_reports(status?, template?, date_from?, date_to?)`, `get_report(report_id)`, `get_report_template(name)`, `get_active_document_version(title)`. Пример: «Какие мои отчёты в статусе needs_review и чего в них не хватает по процедуре?»
- FR-18. Аргументы каждого вызова проверяются схемой. Неизвестная функция или неверные аргументы возвращаются модели как ошибка инструмента, а не как исключение сервиса.
- FR-19. Инструменты выполняются с правами текущего пользователя; идентификатор пользователя никогда не приходит от модели. Officer видит только свои отчёты, captain — все.
- FR-20. Ограничения: не более 4 шагов вызова, таймаут на шаг и на запрос; при превышении — честный ответ, что данные получить не удалось.
- FR-21. Аудит: каждый вызов записывается в `tool_calls` (шаг, имя, аргументы, успех, длительность).
- FR-22. Цитаты в ответе агента проходят проверку FR-6 по фрагментам, которые вернул `search_procedures` в этом же запросе.
- FR-23. Eval агента `eval/agent_golden.yaml` (10 сценариев): точность выбора инструмента, корректность аргументов, отсутствие запрещённых вызовов, корректность итогового ответа; плюс сценарии prompt injection.

## 4. Нефункциональные требования

| Область | Требование |
|---|---|
| Качество | цели (не обещания): hit@5 ≥ 0.8 на золотом наборе, 100% корректность цитат после проверки FR-6, точность выбора инструмента агентом измеряется в eval |
| Производительность | цель p95 ответа ≤ 8 с на локальном стенде (замерить, не заявлять заранее) |
| Безопасность | JWT, роли, argon2, секреты только через переменные окружения; rate limit на `/auth/login`, `/ask`, `/agent/ask`; текст документов, вопросов и результатов инструментов — недоверенные данные (prompt injection); инструменты агента только на чтение; чужие отчёты и журнал → 404 (защита от IDOR); загрузка файлов: лимит размера, тип по сигнатуре, защита от zip-бомб DOCX, парсинг только в worker с таймаутом; контейнер не от root; в логах нет токенов и паролей; `pip-audit` и `gitleaks` в CI |
| Надёжность | таймауты и ретраи вызовов LLM, понятные ошибки (503) при недоступности провайдера |
| Наблюдаемость | структурные логи, метрики Prometheus, таблица аудита запросов и вызовов инструментов |
| Воспроизводимость | запуск одной командой (`docker compose up`), фиксированные версии зависимостей |
| Лицензии/данные | корпус синтетический или с открытой лицензией; тексты IMO и коммерческих SMS в репозиторий не добавлять |

### Инженерные правила
- **Архитектура:** API и CLI не обращаются к хранилищу — только через сервис модуля. Ядро модуля (domain, ports, service) не импортирует фреймворки. Обе границы проверяет import-linter в CI.
- **Мёртвого кода нет:** порог покрытия 95% с учётом ветвлений; абстракция появляется только тогда, когда у неё есть вторая реализация или потребитель.
- **Промпты** — файлы `src/chartroom/<module>/prompts/<name>.v<N>.md`, не строки в коде. Версия промпта пишется в `queries.prompt_version`; изменение промпта — новая версия и прогон eval.
- **README** — один экран: что это, запуск, реальные метрики с датой и коммитом, ссылки на `docs/`. Подробности — в `docs/`.
- **Коммиты:** одна логическая правка на коммит, каждый проходит линтеры и тесты; Conventional Commits; без строк соавторства.
- **`docs/ai-log.md`:** честный журнал — где ИИ ошибся, как поймали, что изменили.

## 5. Архитектура

**Стиль.** Модульный монолит (FastAPI) + отдельный worker. Модули по предметным областям, внутри каждого — порты и адаптеры (ADR-001, ADR-003). Зависимости только внутрь; внешние сервисы (LLM, эмбеддинги, Qdrant, парсер, БД) — за `Protocol`-портами, связывание в `bootstrap.py`. Каждый модуль объявляет узкий порт под свои нужды (принцип разделения интерфейсов, ISP); один адаптер (например, Gemini) может реализовать несколько портов.

```
client (HTTP: HTMX UI / Swagger · CLI)
        │
   main.py (create_app, маппинг ошибок) ── bootstrap.py (точка сборки)
        │
   модули: identity · knowledge · qa · reports · agent · evaluation
        │   каждый: api.py → service.py → ports.py → domain.py
        │           adapters/ реализуют ports
        ├── PostgreSQL (метаданные, пользователи, аудит, отчёты)
        ├── Qdrant (dense + sparse векторы чанков)
        ├── Gemini (генерация, structured output, function calling, эмбеддинги)
        └── Redis ← Celery worker (индексация, пакетная оценка, rate limit)
```

### RAG-конвейер
1. **Парсинг**: PDF → текст с сохранением структуры (заголовки, номера пунктов, страницы).
2. **Чанкинг**: по заголовкам, фрагмент не пересекает раздел; до 500 токенов, перекрытие целыми предложениями до 50 токенов; в метаданных `section_path` (например «Fire / 3.2»). Минимальный размер не задаётся — решение по eval (ADR-004).
3. **Эмбеддинги**: многоязычная модель (RU+EN); dense + sparse (BM25-подобный) вектор на чанк.
4. **Поиск**: Qdrant Query API, гибрид dense+sparse со слиянием RRF, top-20.
5. **Реранкинг**: cross-encoder (опционально) → top-5.
6. **Политика отказа**: если лучший score ниже порога или чанков мало, ответ «нет данных» без вызова генерации.
7. **Генерация**: системный промпт из файла «отвечай только по контексту, цитируй, при отсутствии данных скажи об этом»; structured output `{answer, citations[], refusal}`.
8. **Пост-проверка**: валидатор цитат (FR-6), нормализация языка.

### Цикл агента (M4)
`вопрос → модель (tools) → function_call → проверка аргументов → выполнение в сервисе с правами пользователя → function_response → … (≤ 4 шагов) → ответ → проверка цитат`.

### Модель данных (PostgreSQL)
`users(id, email, password_hash, role)` ·
`documents(id, title, title_key, language)` ·
`document_versions(id, document_id, label, issued_on, filename, checksum, content, status, error, is_active, uploaded_at)` — статус индексации хранится у версии (ADR-005) ·
`chunks(id, version_id, chunk_index, section_path, page, text_hash, qdrant_id)` ·
`queries(id, user_id, mode, question, language, answer, refusal, latency_ms, model, prompt_version, created_at)` ·
`citations(id, query_id, chunk_id, quote)` ·
`tool_calls(id, query_id, step, name, args_json, ok, latency_ms)` ·
`feedback(id, query_id, useful, comment)` ·
`report_templates(id, name, schema_json, version)` ·
`reports(id, template_id, user_id, source_text, data_json, status)` ·
`report_issues(id, report_id, field, message)` ·
`eval_runs(id, git_sha, metrics_json, created_at)`.

## 6. Технологический стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12 | основной стек автора |
| Веб | FastAPI + Pydantic v2 | async, схемы, автодокументация, нативный structured output |
| БД | PostgreSQL 16, SQLAlchemy 2.x (async, asyncpg), Alembic | стандарт, автор владеет |
| Векторы | Qdrant (dense + sparse, RRF) | гибридный поиск из коробки, уже в портфолио (BLACK ICE) |
| Очередь | Celery + Redis | знаком автору; индексация и eval в фоне |
| LLM | Gemini через `google-genai` за портами модулей | опыт автора, function calling и structured output, заменяемо на Claude/OpenAI |
| Эмбеддинги | многоязычная модель за портом `Embedder`; по умолчанию API Gemini, альтернатива BGE-M3 локально | RU+EN, переключение конфигом |
| Реранкинг | BGE-reranker (опционально) | прирост качества поиска |
| Парсинг | PyMuPDF, python-docx | структура и страницы |
| Конфиг | pydantic-settings | типизированная конфигурация |
| UI | Jinja2 + HTMX (+ Tailwind по CDN) | минимальный чат без отдельной JS-сборки |
| Auth | PyJWT, pwdlib (argon2) | просто и безопасно |
| Качество | uv, ruff, mypy --strict, pytest (+pytest-asyncio, httpx, pytest-cov), import-linter, pre-commit | быстрый воспроизводимый цикл, границы слоёв проверяются машиной |
| Безопасность цепочки | pip-audit, gitleaks | уязвимые зависимости и случайные секреты ловятся в CI |
| Логи и метрики | structlog, prometheus-fastapi-instrumentator | наблюдаемость без лишнего |
| Инфра | Docker Compose, Makefile, GitHub Actions | запуск одной командой, CI |

Версии зафиксированы в `uv.lock`. Решения — короткими ADR (`docs/adr/`).

## 8. Тестирование
- **Домен**: чистые unit-тесты без моков (роли, политика отказа, валидаторы отчётов, чанкинг, валидатор цитат).
- **Сервисы**: unit-тесты на in-memory фейках портов.
- **Контракты**: один набор тестов гоняется и на фейке, и на реальном адаптере (Postgres, Qdrant) — фейк не может разойтись с реальностью.
- **Интеграция**: Postgres и Qdrant в Docker, схема — настоящими миграциями, транзакция на тест с откатом.
- **LLM**: мок за портом с фикстурами; для агента — сценарный мок, который возвращает заданную последовательность `function_call`. Реальный LLM — только в eval.
- **Безопасность**: тесты IDOR (чужой отчёт → 404), prompt injection в документах и результатах инструментов.
- **Архитектура**: контракты import-linter; покрытие ≥ 95% с ветвлениями.
- **E2E**: `docker compose up` + сценарий загрузка → вопрос → отчёт → вопрос агенту.
- **Eval** (M3, FR-23) — отдельная метрика качества.

## 10. Критерии готовности (Definition of Done)
- `docker compose up` поднимает всё; первая индексация, вопрос и вопрос агенту работают по README.
- Линтеры, контракты слоёв и тесты зелёные в CI; покрытие ≥ 95% с ветвлениями.
- `make eval` воспроизводим; результаты в README **реальные**, с датой и коммитом.
- Все цитаты в ответах проходят проверку FR-6, в том числе у агента.
- Агент не может получить данные сверх прав пользователя (тесты IDOR и prompt injection зелёные).
- История — атомарные коммиты без строк соавторства; `docs/ai-log.md` ведётся.
- Автор объясняет устройство каждого модуля без подсказок.

## 11. Риски
| Риск | Митигация |
|---|---|
| Нет реальных SMS | авторский синтетический корпус, честная пометка «демо» |
| Галлюцинации | ответ только по контексту, отказ, проверка цитат, eval |
| Агент вызывает не тот инструмент или с неверными аргументами | проверка схемой, ошибка инструмента возвращается модели, лимит шагов, eval FR-23 |
| Утечка данных через инструменты | пользователь берётся из токена, инструменты только на чтение, тесты IDOR |
| Prompt injection через документы и результаты инструментов | данные отделены от инструкций, разрешённый список функций, eval-сценарии атак |
| Расползание объёма | backlog, стоп-правило |
| Стоимость API | кеш эмбеддингов, мок LLM в тестах, малый корпус |
| Авторские права | только синтетические и открытые документы |
| Непонимание кода автором | короткое объяснение модулей после каждого шага, ADR, `docs/ai-log.md` |
