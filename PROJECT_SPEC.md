# ТЗ: Chartroom

Демонстрационный backend-проект «ассистент по судовым процедурам и отчётам».
Автор ТЗ: роль «архитектор + старший разработчик». Статус: черновик на согласование. Код не написан.

---

## 1. Цель и границы

**Цель.** Показать работодателям (backend + AI + морская тематика) связку: знание судового документооборота + умение построить надёжный RAG-сервис.

**Это демонстрация, не продукт.** Не позиционируется как production. Реальных данных судоходных компаний нет, корпус документов синтетический.

**Решаемые боли (подтвердить автором по своему опыту):**
1. Быстро найти нужную процедуру SMS/ISM (тревога, аудит, проверка PSC) и увидеть, где именно это написано.
2. Отчёты и чек-листы вручную: ошибки, пропущенные поля, дубли.

**Входит в объём (MVP):**
- M1. Вопросы по процедурам со ссылками на источник и отказом «в документах нет ответа».
- M2. Извлечение структурированных отчётов и чек-листов из свободного текста с проверкой полноты.
- M3. Оценка качества поиска и ответов на размеченном наборе вопросов.

**Не входит (backlog):** PMS и техобслуживание, анализ рейсов, обмен «судно — берег», мобильное приложение, мультитенантность, реальные интеграции с судовыми системами.

## 2. Пользователи и роли

| Роль | Права |
|---|---|
| `admin` | загрузка и версионирование документов, управление пользователями и шаблонами отчётов |
| `captain` | вопросы, отчёты, просмотр журнала запросов всех |
| `officer` | вопросы, отчёты, просмотр своего журнала |

## 3. Функциональные требования

### M1. RAG по процедурам
- FR-1. Загрузка PDF/DOCX/TXT/MD с метаданными (название, версия, язык, дата).
- FR-2. Асинхронная индексация (парсинг → чанки → эмбеддинги → Qdrant), статус задачи доступен по API.
- FR-3. Вопрос на русском или английском → ответ на языке вопроса.
- FR-4. Каждый ответ содержит цитаты: документ, раздел (путь заголовков), страница, фрагмент текста.
- FR-5. Если релевантных фрагментов недостаточно — отказ с текстом «В загруженных документах ответа нет» (без догадок).
- FR-6. Проверка цитат: каждая ссылка в ответе должна указывать на фрагмент, реально переданный в контекст модели; иначе ссылка удаляется, ответ помечается `citation_warning`.
- FR-7. Обратная связь на ответ (полезен/нет, комментарий).
- FR-8. Версионирование: новая версия документа не теряет старую; поиск по умолчанию только по актуальной.

### M2. Отчёты и чек-листы
- FR-9. Шаблоны отчётов задаются JSON-схемой (поля, типы, обязательность, диапазоны).
- FR-10. `POST /reports/extract`: текст отчёта + шаблон → заполненная структура (structured output).
- FR-11. Валидация: обязательные поля, типы, диапазоны, согласованность (например, ROB не отрицательный). Результат: `data` + `issues[]` (поле, причина).
- FR-12. Сохранение отчёта, статус `draft | needs_review | accepted`.
- FR-13. Набор шаблонов определяет автор по собственному опыту (стартовый набор: суточный отчёт, чек-лист учебной тревоги, швартовая операция). Поля помечены «подтвердить автором».

### M3. Оценка качества
- FR-14. Золотой набор `eval/golden.yaml`: 30 вопросов (20 с ответом, 5 без ответа, 5 на другом языке) с ожидаемым разделом.
- FR-15. Команда `make eval` считает: hit@k (нужный раздел в топ-k), MRR, точность отказов, корректность цитат, долю ответов с `citation_warning`. Результаты сохраняются в `eval/results/*.json` и подставляются в README.

## 4. Нефункциональные требования

| Область | Требование |
|---|---|
| Качество | цели (не обещания): hit@5 ≥ 0.8 на золотом наборе, 100% корректность цитат после проверки FR-6 |
| Производительность | цель p95 ответа ≤ 8 с на локальном стенде (замерить, не заявлять заранее) |
| Безопасность | JWT, роли, хэширование паролей argon2, секреты только через переменные окружения, rate limit на `/ask`, текст документов считается недоверенными данными (защита от prompt injection) |
| Надёжность | таймауты и ретраи вызовов LLM, понятные ошибки при недоступности провайдера |
| Наблюдаемость | структурные логи, метрики Prometheus, таблица аудита запросов |
| Воспроизводимость | запуск одной командой (`docker compose up`), фиксированные версии зависимостей |
| Лицензии/данные | корпус синтетический или с открытой лицензией; тексты IMO и коммерческих SMS в репозиторий не добавлять |

## 5. Архитектура

**Стиль.** Модульный монолит (FastAPI) + отдельный worker. Границы по слоям, зависимости через интерфейсы (портов/адаптеров), чтобы заменять LLM и векторное хранилище.

```
client (HTMX UI / Swagger)
        │
   FastAPI app ── api/ (роутеры, схемы)
        │            services/ (use-case: ask, ingest, extract, evaluate)
        │            domain/ (сущности, правила, политики отказа)
        │            adapters/
        │               llm/ (Gemini, интерфейс LLMClient)
        │               embeddings/ (интерфейс Embedder)
        │               vectorstore/ (Qdrant, интерфейс VectorStore)
        │               parsing/ (PyMuPDF, DOCX)
        ├── PostgreSQL (метаданные, пользователи, аудит, отчёты)
        ├── Qdrant (dense + sparse векторы чанков)
        └── Redis ← Celery worker (индексация, пакетная оценка)
```

### RAG-конвейер
1. **Парсинг**: PDF → текст с сохранением структуры (заголовки, номера пунктов, страницы).
2. **Чанкинг**: по заголовкам, 300–500 токенов, перекрытие ~50, в метаданных `section_path` (например «Fire / 3.2»).
3. **Эмбеддинги**: многоязычная модель (RU+EN); dense + sparse (BM25-подобный) вектор на чанк.
4. **Поиск**: Qdrant Query API, гибрид dense+sparse со слиянием RRF, top-20.
5. **Реранкинг**: cross-encoder (опционально) → top-5.
6. **Политика отказа**: если лучший score ниже порога или чанков мало, ответ «нет данных» без вызова генерации.
7. **Генерация**: системный промпт «отвечай только по контексту, цитируй, при отсутствии данных скажи об этом»; structured output `{answer, citations[], refusal}`.
8. **Пост-проверка**: валидатор цитат (FR-6), нормализация языка.

### Модель данных (PostgreSQL)
`users(id, email, password_hash, role)` ·
`documents(id, title, language, status)` ·
`document_versions(id, document_id, version, checksum, uploaded_at, is_active)` ·
`chunks(id, version_id, section_path, page, text_hash, qdrant_id)` ·
`queries(id, user_id, question, language, answer, refusal, latency_ms, model, created_at)` ·
`citations(id, query_id, chunk_id, quote)` ·
`feedback(id, query_id, useful, comment)` ·
`report_templates(id, name, schema_json, version)` ·
`reports(id, template_id, user_id, source_text, data_json, status)` ·
`report_issues(id, report_id, field, message)` ·
`eval_runs(id, git_sha, metrics_json, created_at)`.

## 6. Технологический стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12 | основной стек автора |
| Веб | FastAPI + Pydantic v2 | async, схемы, автодокументация, нативный structured output |
| БД | PostgreSQL 16, SQLAlchemy 2.0 (async, asyncpg), Alembic | стандарт, автор владеет |
| Векторы | Qdrant (dense + sparse, RRF) | гибридный поиск из коробки, уже в портфолио (BLACK ICE) |
| Очередь | Celery + Redis | знаком автору; индексация и eval в фоне |
| LLM | Gemini через `google-genai` за интерфейсом `LLMClient` | опыт автора, заменяемо на Claude/OpenAI |
| Эмбеддинги | многоязычная модель через интерфейс `Embedder`; по умолчанию API Gemini, альтернатива BGE-M3 локально | RU+EN, переключение конфигом |
| Реранкинг | BGE-reranker (опционально) | прирост качества поиска |
| Парсинг | PyMuPDF, python-docx | структура и страницы |
| Конфиг | pydantic-settings | типизированная конфигурация |
| UI | Jinja2 + HTMX (+ Tailwind по CDN) | минимальный чат без отдельной JS-сборки |
| Auth | PyJWT, pwdlib (argon2) | просто и безопасно |
| Качество | uv, ruff, mypy, pytest (+pytest-asyncio, httpx), pre-commit | быстрый и воспроизводимый dev-цикл |
| Логи и метрики | structlog, prometheus-fastapi-instrumentator | наблюдаемость без лишнего |
| Инфра | Docker Compose, Makefile, GitHub Actions | запуск одной командой, CI |

Версии зафиксировать в `uv.lock`. Решения оформить короткими ADR (`docs/adr/`).

## 8. Тестирование
- Unit: чанкинг, валидатор цитат, политика отказа, валидаторы отчётов.
- Integration: Postgres и Qdrant в Docker (индексация → поиск → ответ с подменой LLM).
- Contract: мок `LLMClient` с фикстурами; реальный LLM только в eval.
- E2E: `docker compose up` + сценарий загрузка → вопрос → отчёт.
- Eval (M3) как отдельная метрика качества.

## 10. Критерии готовности (Definition of Done)
- `docker compose up` поднимает всё; первая индексация и вопрос работают по README.
- Тесты и линтеры зелёные в CI; покрытие ядра (чанкинг, цитаты, отказ, валидаторы) проверяется порогом.
- `make eval` воспроизводим; результаты в README **реальные**, с датой и коммитом.
- Все цитаты в ответах проходят проверку FR-6.
- Автор объясняет устройство каждого модуля без подсказок.

## 11. Риски
| Риск | Митигация |
|---|---|
| Нет реальных SMS | авторский синтетический корпус, честная пометка «демо» |
| Галлюцинации | ответ только по контексту, отказ, проверка цитат, eval |
| Расползание объёма | backlog, стоп-правило, слои 1–2 |
| Стоимость API | кеш эмбеддингов, мок LLM в тестах, малый корпус |
| Авторские права | только синтетические и открытые документы |
| Непонимание кода автором | ежедневное короткое объяснение модулей, ADR, парное ревью |

## 12. Что подтвердить автору до старта
1. Боли и поля шаблонов отчётов соответствуют реальному опыту на судне.
2. Языки корпуса: только RU+EN?
3. LLM-провайдер по умолчанию: Gemini или Claude.
4. Готовность писать сам корпус процедур (10–15 документов).
